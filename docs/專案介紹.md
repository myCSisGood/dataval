# dataval 專案介紹 — 資料設計的治理閘門

> 這份文件是給想「理解這個專案」的人：為什麼做、核心理念、它實際在做什麼。
> 如果你要「使用或維護」這套工具，請看技術文件 `README.md`。

## 為什麼需要它

資料設計的把關，長期以來靠人力與默契。一份 DDL 要不要放行，取決於誰有空看、看的人記得多少規範、當天的嚴格程度如何。於是同樣的問題反覆發生：缺主鍵的表上了線、金額欄位用了浮點數、時間欄位沒有時區，等到報表對不上帳才被發現，修復成本是設計期的數十倍。命名的漂移更隱蔽——同一個「客戶」概念，在不同團隊的表裡叫 cust、client、customer；同一個 email 事實散落在三張表裡，彼此不同步，沒有人說得清哪一份才是真的。而這一切的審查過程不留痕跡：無法重複、無法稽核、標準因人而異。

dataval 要解決的就是這件事：**在 DDL 進入生產之前，用一致、可重複、可稽核的方式自動驗證**，並且在硬規則之外，給設計者語意層次的建議。

## 核心理念：兩區分離

整個系統建立在一個不可動搖的區分上。

**閘門區**負責「合規與否」的判定。它只包含確定性規則——能用「有沒有這個欄位、型別對不對、命名符不符樣式」機械判斷的事。它的三個承諾是：違反會擋、同樣的輸入永遠得到相同結果、不需要任何外部服務。閘門的執行路徑裡沒有 LLM。

**顧問區**負責「值得想想」的提醒。命名的語意一致性、資料主體抓得對不對、這種表該套哪些業界實踐——這些需要理解才能判斷的事，交給 LLM，而它的任何輸出**一律只是提示，永遠進不了合規判定**。措辭上刻意設計成「給設計者思考的提問」而不是結論，因為語意判斷應該啟發人，而不是取代人。

為什麼這個分離如此重要？因為治理的公信力來自一致性。如果「過不過」會因為模型心情而變，閘門就失去意義；反過來，如果只有硬規則而沒有語意建議，工具就只是個冷冰冰的裁判。兩區分離讓確定性與智慧各司其職。

## 一份設計走過的流程

實際的使用體驗刻意做到最輕。設計者把一個 data subject 的 DDL、`relations.yaml` 與 `context.md` 三件必備放進 `input/<名>/`（CSV 樣本選填，沒有樣本仍會產報告，只是樣本相關檢查略過）。Domain knowledge 以 skill 放在 `config/<域>/knowhow/`，複雜規則放在 `config/Common/knowhow_py/`，Mermaid ER 參考模型放在 `config/<域>/erd/`。跑一次 `run.py` 就會合併這些輸入產生報告。ER 關係可協助產生 lineage 候選，但只有 `relations.yaml` 內明確的關係才是確定性宣告。

系統先確認規則是最新的：所有規則會被 compile 成一份結構化的 JSON（`build/compiled_rules.json`），引擎從這份 JSON 載入執行。規則有更新才重新 compile，而這份 JSON 本身就是「這次跑用的是哪一版規則」的權威記錄，可以 diff、可以稽核。

接著是閘門判定。除了逐表的宣告式卡控，還有幾層跨表與跨領域的檢查：跨表的 join key 型別是否一致、同一事實是否散落多表、外鍵引用的目標是否存在；當設計明確指定業務 domain 時，它還會對照 **production 基準區**（已核准上線的 DDL）檢查同概念是否沿用既有命名——production 的 CRM 已經有 `customer_email`，你的新表用 `client_email` 就會被擋下來，並被告知該對齊哪張表。如果一張表看起來像某個主體的權威表、但這個主體還沒登錄在 SSOT registry 裡，系統會發出警告提醒「先登錄再上線」（不擋），並把候選整理好，等人確認後寫回 registry。

報告的呈現哲學是「從裁判變教練」。開頭直接說結論：合規或不合規、被哪幾條規則卡下來；Lineage 區塊再用「來源 → 目標 → 欄位映射」呈現關係，明確區分 YAML 宣告與系統建議。Case config 沒有 lineage 時，工具只依 Business Key 或共用 `*_id` 在顧問區提出候選，不把推測當成事實。每條違規以固定的四問呈現——哪條規則、哪裡違反、期望與實際的並列對照、以及具體怎麼修。「MonthlyPrice 是 Float64，期望 Decimal(P,S)，改成 Decimal(18,2)」——設計者不需要去翻規範文件，照著修就是。通過的項目則彙總成一行，不會淹沒真正需要注意的違規。

最後是顧問區。`run.py` 每次都直接產出 HTML；沒接本地 LLM 時，確定性卡控、checking rule ID、lineage 與合規結果仍完整可看，只有語意規則清楚標示「待補完」。同時產生的指示可交給 agent 補建議，再由 `merge_advisory.py` 更新三種報告。回填 JSON 必須先通過正式 schema，合併前後的閘門 findings 也會直接逐項比對，因此補顧問內容不可能改變合規判定。

## 規則是文件，也是程式

dataval 的規則採 policy-as-code 風格：**一條規則就是一份 Markdown 規範文件**。文件的主體是給人讀的——這條規則的目的、適用情境、違反後果、建議怎麼修；文件的最後用一個程式碼區塊圈出機器執行的卡控。以一條真實規則為例：

````markdown
---
id: txn_amount_needs_currency
enforcement: blocking        ← 這一個字決定會不會擋
---
# 交易金額必須記錄幣別
## 目的
交易表記錄金額卻沒有幣別，跨幣別時無法解讀，對帳出錯。
## 修正建議
新增 currency LowCardinality(String)。
## 卡控
```check
applies_to: name_matches ".*(transaction|billing).*"
require: has_column currency
```
````

一張 `billing_event` 表有 amount 卻沒有 currency 送進來，報告會產出：會擋、違反位置 billing_event、期望「表上有欄位 currency」、實際「欄位不存在」、修法「新增 currency LowCardinality(String)」——修法正是規則作者寫在文件裡的那句話，寫一次、每份報告受益。

這個設計讓規則的維護成本降到最低：**一條規則一個檔案**，新增等於丟一個檔、停用等於移走一個檔、調嚴格度等於改一個字。規則不藏在引擎裡——domain skills 住在 `config/<域>/knowhow/`，Common 每次必載，PLM、FCM、CRM、SCM 等依設計歸屬載入。需要跨表或樣本能力的邏輯放入 `config/Common/knowhow_py/`。語意規則使用 `check-llm`，只進顧問區。

命名規則還有一個省力設計：與其寫一堆正則，不如維護一份**詞彙字典**——禁用詞對應標準詞（cust → customer）、別名對應正規詞（client → customer）。卡控直接對照字典，字典也同時支撐著 production 的「同概念異名」偵測。

## 一致性不是承諾，是驗證出來的

治理工具最怕的是「今天過、明天不過，沒人知道為什麼」。dataval 用三層機制把一致性變成可驗證的性質。

第一層是架構：閘門區被設計成純函數——輸出只由 DDL 與規則集決定，無 LLM、無網路、無時間、無隨機。第二層是**checking rule ID 結果摘要**：每份報告直接列出哪些 rule ID 擋下、警告、通過或略過，不用指紋或代碼代表結果，人可以直接讀懂這次執行了哪些檢查。第三層是**黃金測試**：基準 DDL 的閘門輸出被存檔，任何改動後跑一次比對，防止改 A 規則誤傷 B；再加上「連跑兩次 checking rule ID 結果必須一致」與「接上一個亂回傳的假 LLM，閘門 rule ID 結果必須不變」兩類測試。這套守門在開發過程中真的抓到過肉眼看不出的行為漂移——它的價值已經被實證，不是理論。

## 越用越強的三個循環

這套系統不是靜態的檢查器，它被設計成會隨使用而變強。不合規的設計照著報告的修法改完重送，直到合規——這是最短的循環。合規且經 owner 核准的設計被放入 production，成為之後命名對照的基準——閘門的守備範圍隨著每一份被認可的設計而擴大。而顧問區的發現、未登錄主體的候選，經人確認後沉澱成 registry 條目與新的規則檔——語意層的智慧逐步「畢業」成確定性的閘門。三個循環的共同點是：每一次變化都可以直接 diff 規則檔，報告也以 checking rule ID 明確呈現行為，可解釋、可追溯——系統越用越強，而不失控。

## 需要大家一起填實的部分

工具與機制已經就緒，但治理內容必須來自領域知識：領域專家提供真實 hard rule 與語意檢查點；治理負責人維護詞彙字典；資料 owner 登錄 SSOT registry；DBA 提供 production 基準 DDL；設計提交者提供 DDL、情境與 relations 三件必備（樣本選填）。規則寫 Markdown、registry 與 relations/context 使用 YAML front-matter、核准 DDL 放進 production，都是可直接 diff 的小檔案。

## 現況與方向

目前具備 Markdown 與 Python 規則、宣告式 checking verbs、production 基準與設計 lineage 卡控。規則 lint、架構測試、黃金測試與語法檢查由 GitHub Actions 在 Python 3.10、3.11、3.12 執行。下一步應優先換上真實 domain 規則、擴充跨 domain 測試；外部 metadata 或 runtime lineage 只有在有真實介面與可測試策略時才加入。

一句話總結這個專案想達到的狀態：**讓每一條沉澱下來的 know-how，都使閘門更完整、顧問更聰明。**
