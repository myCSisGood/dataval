# dataval 規則總覽（規則手冊）

_規則版本碼由 `build/compiled_rules.json` 產生；逐條權威清單見自動生成的
`docs/規則索引.generated.md` ｜ 來源：`config/<域>/knowhow/`、
`config/Common/knowhow_py/`、引擎內建檢查_

## 閱讀指引

**兩區**：閘門區（gating）＝確定性、可重現、會影響合規判定，執行路徑零 LLM；
顧問區（advisory）＝LLM 語意建議，只提示、永不影響判定（`_enforce_zone` 在程式層強制）。

**等級**：🔴 blocking（會擋，合規判定 = 不合規）／🟡 warning（警告放行）／
🔵 advisory（顧問提問）／⚪ info（純資訊）。

**四類**：結構（structural）、命名（naming）、最佳實踐（best_practice）、SSOT。

**規則的三種形態**：宣告式 `.md`（`config/<域>/knowhow/gating|advisory/`，一條一檔）、
程式式 `.py`（`config/Common/knowhow_py/`，跨表或需樣本的複雜邏輯）、引擎內建
（lineage／正式區／全域圖等治理機制，checking rule ID 固定）。

# 第一部：閘門區（確定性，影響合規判定）

## A. Common 宣告式規則（17 條，所有 domain 恆載入）

### A1. 結構類（5 條）

| 規則 | 等級 | 卡控動詞 | 詳細說明 |
|---|---|---|---|
| `structural_order_by` | 🔴 | `has_order_by` | 每張表必須有 `ORDER BY`。MergeTree 家族依 ORDER BY 建立稀疏索引，缺少它等於放棄索引——所有查詢退化為全表掃描。修法：以最常用的過濾欄位組合設定排序鍵。 |
| `structural_engine_mergetree` | 🔴 | `engine_matches MergeTree` | 明細層資料必須使用 MergeTree 家族引擎（MergeTree / ReplacingMergeTree / SummingMergeTree 等）。其他引擎（Log、Memory）不具備合併、索引與 TTL 能力，不適合正式資料資產。 |
| `structural_key_not_nullable` | 🔴 | `no_nullable_in_key` | 主鍵／排序鍵欄位不可為 `Nullable`。Nullable 鍵會破壞合併與去重語意（NULL ≠ NULL），且每個 Nullable 欄位帶額外的標記子欄開銷。修法：鍵欄位改 NOT NULL，未知值以業務預設值表達。 |
| `structural_business_key` | 🔴 | `has_business_key` | 每張表必須有穩定的業務識別鍵（business key）。ClickHouse 的 ORDER BY 與 PRIMARY KEY 都是物理索引語意，不保證業務唯一性；業務鍵必須由 context.md 的 front-matter `business_keys` 明確宣告。 |
| `structural_audit_columns` | 🟡 | `has_column created_at`＋`has_column updated_at` | 表應具備稽核欄位 `created_at` / `updated_at`。稽核欄位支撐血緣追蹤與變更歷史，是「這筆資料何時進來、何時被改」的最低限度可觀測性。 |

### A2. 命名類（7 條）

| 規則 | 等級 | 卡控動詞 | 詳細說明 |
|---|---|---|---|
| `naming_table_snake_case` | 🔴 | `table_name_matches [a-z][a-z0-9_]*` | 表名必須 snake_case 全小寫。一致的表名讓資產可預測、可被工具與腳本機械處理；混用大小寫在不同用戶端的引號行為不一，是隱性錯誤來源。 |
| `naming_column_case` | 🔴 | `all_columns_name_match [a-z][a-z0-9_]*` | 全部欄位名必須 snake_case 全小寫。欄位命名樣式一致是資料字典與自動化（程式產生 SQL、對照 metadata 平台）的基礎。 |
| `naming_columns_commented` | 🔴 | `all_columns_commented` | 每個欄位都必須有 `COMMENT`。欄位註解是資料字典的最小單位，中介資料平台（如 DataHub）會直接讀取；沒有註解的欄位對下游消費者是黑箱。 |
| `naming_glossary` | 🟡 | `no_banned_term`＋`no_alias_term` | 命名對照 `config/glossary.yaml` 詞彙字典：禁用縮寫（cust→customer、qty→quantity、amt→amount、dt→date、ts→timestamp、usr→user、num→number、desc→description、addr→address）與別名（client/buyer/member→customer、goods/item/sku→product）。字典式管理比堆正則易維護——加詞只改 YAML。 |
| `naming_pk_suffix` | 🟡 | `pk_ends_with _id` | 主鍵欄位建議以 `_id` 結尾。可預測的鍵名讓 join 推斷（含本工具的關係建議）與人的理解都更容易。 |
| `naming_reserved_words` | 🟡 | `columns_not_named select,from,where,table,order,group,index,key,all` | 欄名避免 SQL 保留字。保留字欄名到處需要跳脫引號，易寫錯且部分工具不相容。 |
| `naming_identifier_length` | 🟡 | `identifier_max_length 64` | 表名／欄名長度 ≤ 64 字元。過長識別字不利閱讀，且部分下游工具有長度上限。 |

### A3. 最佳實踐類（4 條）

| 規則 | 等級 | 卡控動詞 | 詳細說明 |
|---|---|---|---|
| `bp_no_float` | 🔴 | `type_not_used Float` | 全表禁用 Float 型別。浮點數不適合需要精確比較與彙總的數值——`0.1+0.2≠0.3` 這類誤差在對帳與彙總場景是靜默毒藥。需要小數用 Decimal，需要近似值的科學計算場景另案評估。 |
| `bp_money_decimal` | 🔴 | `type_not_for_matching .*(amount\|price\|cost\|balance\|fee\|revenue\|salary).* float` | 名稱含 amount/price/cost/balance/fee/revenue/salary 的金額欄位不可為浮點。金額用浮點必然對帳不平。修法：`Decimal(18, 2)` 或依幣別精度調整。 |
| `bp_lowcardinality_status` | 🔴 | `lowcardinality_when_present status` | 表中存在 `status` 欄位時必須用 `LowCardinality(String)`。低基數高重複欄位以 LowCardinality 儲存可大幅節省空間與查詢記憶體。 |
| `bp_datetime_timezone` | 🟡 | `datetime_with_timezone` | DateTime 欄位應標明時區（如 `DateTime('UTC')`）。時區不明的時間在跨區情境無法正確比較，遲到資料歸期會出錯。 |

### A4. SSOT 類（1 條）

| 規則 | 等級 | 卡控動詞 | 詳細說明 |
|---|---|---|---|
| `ssot_pii_amount_split` | 🟡 | `columns_not_both customer_email MonthlyPrice` | PII 與金額不應混存同表。混存使權限難以分級（看金額的人不需要看個資）、真實源歸屬模糊。此規則目前以示範欄位組合實作，PII pattern 偵測的泛化版在 roadmap。 |

## B. 領域宣告式規則（按需載入）

### PLM（2 條 gating）

| 規則 | 等級 | 卡控動詞 | 詳細說明 |
|---|---|---|---|
| `plm_part_master_baseline` | 🔴 | `applies_to: name_matches ".*(part\|item\|material).*"`＋`has_column part_no`＋`has_column revision` | 料件主檔（表名含 part/item/material）必須具備 `part_no` 料號與 `revision` 版次。料件主檔是所有產品結構的根，缺料號無法被 BOM 引用、缺版次無法版本追溯。 |
| `plm_bom_needs_quantity` | 🔴 | `applies_to: name_matches ".*bom.*"`＋`has_column quantity` | BOM 表（表名含 bom）必須有 `quantity` 用量欄位。BOM 表達產品由哪些子件組成，缺用量無法展開物料需求（MRP）與成本。 |

### SCM（3 條 gating）

- `scm_supplier_baseline`：供應商主檔基線。
- `scm_po_needs_supplier`：採購單必須關聯供應商。
- `scm_grn_needs_po`：收貨單必須關聯採購單。

BLM 與 FCM 各有一條 warning 基線規則；CRM 目前以 glossary、SSOT、ERD 與 flow
為主。逐條執行內容與最新數量以 `docs/規則索引.generated.md` 為準。

## C. Python 程式式規則（`config/Common/knowhow_py/`，6 條，跨表／需樣本邏輯）

| 規則 | 類別 | 等級 | 詳細說明 |
|---|---|---|---|
| `structural_fk_resolves` | 結構 | 🔴 | **FK 目標必須存在**（跨表）。欄名形如 `<表>_id` 且該表存在於本次 schema 時，驗證引用可解析；指向不存在的表即擋。 |
| `structural_type_sample` | 結構 | 🔴 | **宣告型別 vs 樣本一致**（需樣本）。逐欄比對 DDL 宣告型別與 `samples/*.csv` 實際值的型別形狀——宣告 UInt64 但樣本是字串、宣告 Date 但樣本非日期，均會擋。這是「DDL 說一套、資料長另一套」的第一道防線。 |
| `ssot_authority` | SSOT | 🔴 | **權威唯一性**（依 `config/default.yaml` 的 SSOT registry，跨表）。registry 宣告某實體的權威表後：權威表在場時檢視其形狀、同一實體出現第二個疑似權威即擋。守「一個事實只有一個真實源」。 |
| `ssot_join_keys` | SSOT | 🔴/🟡 | **跨表 join key 相容性**（跨表＋需樣本）。同名鍵欄位跨表比對：型別不一致（String vs UInt64）→ 會擋；型別相同但樣本值編碼不一致（`1001` vs `0001001` 前導零補齊）→ 警告。編碼檢查依賴 CSV 樣本的前導零保留慣例。 |
| `ssot_fact_duplication` | SSOT | 🔴 | **同一事實不可散落多表**（依 registry 的 `attribute_owner`）。屬性宣告了擁有表之後，其他表再承載同一屬性（如 customer_email 同時存在 dim_customer 與 subscription）即擋——重複承載必然漂移。 |
| `no_future_event_time` | 最佳實踐 | 🟡 | **時間欄位不應有可疑靜態預設值**。event-time 類欄位設固定日期預設值（而非 `now()` 或不設）通常是錯誤，會汙染時間彙總。 |

## D. 引擎內建確定性檢查（治理機制，checking rule ID 固定）

### D1. 關聯與 lineage（宣告面，`relations.yaml` → declared lineage）

| Checking rule | 等級 | 詳細說明 |
|---|---|---|
| `LINEAGE.METADATA` | ⚪/🟡 | lineage 宣告的載入與格式狀態；宣告缺漏或格式問題在此呈現。 |
| `LINEAGE.UPSTREAM_EXISTS` | 🔴 | 宣告的上游表必須存在。本地端點（`local.<表>`）對本次 schema 驗證；跨 domain 端點（`<DOMAIN>.<表>`）對 `production/<DOMAIN>/` 的已核准 DDL 實檢。引用不存在的上游即擋。 |
| `LINEAGE.COLUMN_EXISTS` | 🔴 | 欄位映射的來源欄位必須存在於上游表。表在但欄位不在（改名、拼錯）即擋。 |
| `LINEAGE.TYPE_COMPATIBILITY` | 🔴 | 下游欄位與上游來源欄位的型別必須相容。String 引用 UInt64 這類不相容映射即擋——它是 join 靜默失敗的根源（實例：subscription 示範案例被此規則攔下）。 |
| `LINEAGE.CYCLE` | 🔴 | 本次宣告的關聯在 subject 內不可形成循環依賴。 |
| `LINEAGE.DOMAIN_SCOPE` | 🔴 | 跨 domain 引用的 domain 必須在本次載入的 domain 範圍內（context.md 的 `domains` 宣告）。防止未宣告依賴的偷渡。 |
| `RELATION.CARDINALITY_SAMPLE` | 🔴 | **宣告基數對樣本實檢**。宣告 `N:1` / `1:1` 但「1 的一方」在樣本出現重複鍵 → 宣告與資料矛盾，即擋。基數不是文件，是被驗證的宣告。 |

### D2. 正式區與全域關聯圖

| Checking rule | 等級 | 詳細說明 |
|---|---|---|
| `PRODUCTION.SCOPE` | ⚪ | 正式區參照範圍的狀態（未指定 domain／無可參照 DDL 時標示略過）。 |
| `PRODUCTION.NAMING_CONSISTENCY` | 🔴 | 命名概念一致性：同一正規化概念（經 glossary 別名／禁用詞歸一）在正式區已有核准名稱時，新 DDL 使用不同名稱即擋。防止同概念異名在資產庫擴散。 |
| `PRODGRAPH.SCOPE` | ⚪ | 全域關聯圖參照範圍狀態（正式區無 subject 時略過）。 |
| `PRODGRAPH.CYCLE` | 🔴 | **全域循環**：本 subject 的關聯加入正式區全域圖後出現跨 subject 循環依賴 → 擋。上下游互相引用需拆解。 |
| `PRODGRAPH.CARDINALITY_CONFLICT` | 🔴 | **基數矛盾**：同一對端點（from 表.欄 → to 表.欄）在正式區既有 subject 已宣告不同 cardinality → 擋。同一關聯不可有兩種說法。 |
| `SYSTEM.PRODUCTION_PARSE` | 🔴 | 正式區 DDL 無法解析屬治理資產損壞，即擋並指出需修復的檔案。 |

### D3. SSOT 推斷與輸入診斷

| Checking rule | 等級 | 詳細說明 |
|---|---|---|
| `SSOT.UNREGISTERED_SUBJECT` | 🟡 | **未登錄主體推斷**（確定性啟發層）：schema 中疑似構成獨立 data subject 但未在 SSOT registry 登錄的實體，警告放行並列為候選；候選清單供顧問區產出登錄草稿。 |
| `SYSTEM.DDL_READ`／`SYSTEM.CASE_CONFIG`／`SYSTEM.SAMPLE_SPEC`／`SYSTEM.CONTEXT_SPEC`／`SYSTEM.DOMAIN_SPEC`／`SYSTEM.BUSINESS_KEY_SPEC`／`SYSTEM.LINEAGE_SPEC`／`SYSTEM.ER_DIAGRAM_PARSE` | 🟡 | 輸入載入診斷：個案設定、樣本、語意、domain、business key、lineage、ER diagram 各項的讀取／格式問題以警告呈現在報告中，確保「輸入有問題」本身可見、不被靜默吞掉。 |

## E. 前置檢核（precheck，報告產生前的閘門）

不是 checking rule，而是**更前面的門**：任何一項不過，該 subject 不產生報告
（`run.py` exit code 2，明細寫 `reports/<名>.precheck.md`）。

| 層 | 檢核內容 |
|---|---|
| 存在性 | 三件必備齊全（`<名>.sql`、`relations.yaml`、`context.md`）；`samples/` 為選填，缺樣本不擋、只警告並略過該表 |
| 可解析性 | DDL 可 parse；CSV 表頭可讀且欄數合法；relations YAML 語法與欄位值合法（cardinality ∈ 1:1/N:1/N:M，kind ∈ fk/reference/lookup）；context 有 front-matter `subject` 與必填「粒度」段落 |
| 一致性 | CSV 表頭欄名 ⊆ DDL 欄位；relations 本地端點存在於 DDL；多表 subject 至少一條關聯（單表可 `relations: []` 明示確認無） |

# 第二部：顧問區（LLM 語意建議，只提示不擋）

## F. Common 語意規則（3 條）

| 規則 | 類別 | 詳細說明 |
|---|---|---|
| `naming_semantic` | 命名 | 規則能查字形、查不了語意。檢視整個 schema：縮寫不一致（cust 與 customer 並存）、同概念異名（user_id 與 member_id 指同一實體）、欄名與型別／註解語意不符。以提問語氣回饋；反覆出現的發現應循畢業流程沉澱為確定性規則。 |
| `best_practice_semantic` | 最佳實踐 | 判斷每張表的型態（交易／維度／事件／bridge／PII 存放），列出該型態真正適用的業界實踐並評估符合度。「這是哪種表、該套哪些實踐」需要理解，無法機械判斷。 |
| `ssot_semantic` | SSOT | registry 尚未涵蓋的部分：看似有多個權威擁有者的實體、跨域重複儲存的同一事實、可能不指向同一實體的模糊 join key。為 registry 提名候選。 |

## G. PLM 領域語意規則（4 條）

| 規則 | 詳細說明 |
|---|---|
| `plm_bom_structural_integrity` | BOM 結構完整性：父件／子件關係是否清楚表達（parent/child 或 assembly/component）、用量欄位語意是否自洽、層級展開是否可行。BOM 的結構正確性需要理解語意,不能只靠欄位規則。 |
| `plm_revision_versioning` | 版次控制：是否有明確 revision/version 欄位、能否回答「某時間點的有效版本是哪一個」、歷史版本是否保留可追溯。這是 PLM 有別於一般主檔的關鍵語意。 |
| `plm_lifecycle_stage` | 生命週期階段：是否有表達階段的欄位（概念、設計、量產、停產、EOL）、階段值是否受控值域、階段轉移是否可追溯。 |
| `plm_engineering_change` | 工程變更（ECN/ECO）可追溯性：是否有明確的變更單實體作為變更的單一真實源、變更能否關聯到受影響的料件／BOM 與生效版本。 |

## H. FCM 領域語意規則（1 條）

| 規則 | 詳細說明 |
|---|---|
| `fcm_master_data_semantic` | FCM 主檔治理語意：主檔實體是否有清楚的唯一識別與權威來源、是否存在跨表重複承載同一主檔屬性的風險。 |

## I. 引擎內建顧問輸出

| Checking rule | 詳細說明 |
|---|---|
| `CONCEPT.SUBJECT` | **概念層（`concept.py`）**：獨立於逐條規則之上的資料設計概念檢視，確認主體本身的成立性——以「給設計者的提問」而非結論的語氣呈現。 |
| `LINEAGE.SUGGESTION` | 未宣告關聯時的保守候選：依 business key、共用 `*_id` 欄位推得的可能關係，僅供設計者確認後補進 `relations.yaml`。 |
| `LINEAGE.ER_SUGGESTION` | 依 `config/<域>/erd/*.mmd`（Mermaid）比對 ER 圖與 DDL 的關係差異，提示不一致處。 |
| `PRODGRAPH.IMPACT` | **影響分析**：本 DDL 定義的表在正式區有哪些 subject 依賴（含依賴的欄位路徑）——改動的爆炸半徑。變更前通知依賴方；破壞性變更應開新表版本而非原地修改。 |
