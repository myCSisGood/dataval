# dataval 使用流程與程式碼導覽

> 這份文件把「使用者實際怎麼操作」和「程式碼在背後做了什麼」綁在一起講，
> 依時間順序走一遍完整旅程。想知道「為什麼要做這個專案」看
> `專案介紹.md`；想查「有哪些規則」看 `規則總覽.md`；要新增規則看
> `SKILL_AUTHORING.md`；指令速查表看 `README.md`。這份文件是給要**動手操作、
> 或要維護／擴充程式碼**的人看的逐步導覽，每一步都附對應的檔案與函式。

---

## 全貌：一次完整旅程的九步

```text
0 建環境        python3 -m venv .venv && pip install sqlglot pyyaml
1 準備四件輸入   input/<subject>/{<subject>.sql, samples/*.csv, relations.yaml, context.md}
2 執行驗證       .venv/bin/python run.py
3 讀報告         reports/<subject>.report.{md,json,html}
4 (若不合規)     依報告的「本次卡控摘要」修正輸入，回到步驟 2
5 (可選)補顧問區  依 *.advisory_prompt.md 生成 *.advisory_result.json → merge_advisory.py
6 晉升正式區     .venv/bin/python promote.py <subject>
7 全區健檢       .venv/bin/python production_audit.py（通常排期執行，不是每次都跑）
8 (可選)新增規則  rules.py new / draft / adopt（治理需求變了才需要）
```

步驟 0–4 是**每一個新 data subject**都會走的主線；步驟 5 只在沒有接 LLM
時才需要；步驟 6–7 是**這個 subject 要正式採用**時才做；步驟 8 是**維護規則本身**
（不是驗證某個 DDL）。以下逐步展開，並用專案內附的兩個範例
`input/order/`（合格提交）與 `input/subscription/`（刻意含違規）具體對照。

---

## 步驟 0：建立環境

```bash
python3 -m venv .venv
.venv/bin/pip install sqlglot pyyaml
```

只有兩個外部依賴：`sqlglot`（解析 DDL）與 `pyyaml`（讀 YAML 設定）。
LLM 是選配——不裝任何 LLM SDK，工具照樣能跑出合規判定（見步驟 2、5）。

---

## 步驟 1：準備四件輸入

一個 data subject（一份 DDL 所描述的資料主體）對應 `input/` 下**一個資料夾**：

```text
input/order/
  order.sql            DDL（可含多張 CREATE TABLE）
  samples/
    orders.csv          DDL 每張表各一份樣本，檔名＝表名
    order_items.csv
  relations.yaml        表間關聯（from / to / cardinality）
  context.md            語意描述（front-matter ＋ 段落）
```

四件的角色，對照 `input/order/` 的實際內容：

| 件 | 範例內容 | 誰讀它 |
|---|---|---|
| `order.sql` | 兩張表 `orders`、`order_items`，每個欄位都有 `COMMENT` | 所有規則的檢查對象 |
| `samples/*.csv` | `orders.csv`、`order_items.csv`，欄名對齊 DDL、空格＝NULL | 型別對樣本、join key 編碼一致、cardinality 實檢 |
| `relations.yaml` | `order_items.order_id → orders.order_id`（本地 `N:1`）＋`orders.customer_id → CRM.dim_customer.customer_id`（跨 domain 三段式） | 轉成 declared lineage；跨 domain 端點會對 `production/CRM/` 實檢是否存在 |
| `context.md` | front-matter 宣告 `subject: 訂單`、`domains: [CRM]`、`business_keys`；內文含「粒度」段落逐表寫清楚一行代表什麼 | front-matter 進引擎當設定；「粒度」等段落餵顧問區與概念層 |

這一步完全是**人的工作**，程式碼此時還沒被呼叫。格式細節（CSV 的 NULL 慣例、
relations 的三段式跨 domain 語法、context 的必填段落）見 `input/README.md`。

---

## 步驟 2：執行 `run.py`

```bash
.venv/bin/python run.py
```

零參數，`run.py` 是唯一日常入口。它在背後依序做了六件事：

### 2.1 掃描輸入資料夾 —— `run.py: find_ddls()`

掃 `input/`，找每個子資料夾裡 `<資料夾名>.sql`（新式）或平鋪的 `<名>.sql`
（舊式相容）。掃到的每一份 DDL 各自獨立跑完整流程，互不影響。

### 2.2 規則 compile —— `dataval/compiler.py: ensure_compiled()`

規則是用 Markdown 寫的（`config/<域>/knowhow/{gating,advisory}/*.md`），
但執行時讀的是編譯後的 `build/compiled_rules.json`。`run.py` 每次啟動都會
重新從 `.md` 產生一份結構化內容，**只有內容真的變了才覆寫**這個 JSON
（`main()` 先讀舊檔內容比對，見 `run.py:417-441`）。如果規則集真的變了，
會順便呼叫 `dataval/rules_history.py: record_change()`，把「新增了什麼、
拿掉什麼、哪些欄位被改了（如 enforcement 從 warning 改 blocking）」寫進
`rules_history/CHANGELOG.md` 與一份帶時間戳與版本碼的 JSON 快照——這是規則
版本可追溯的機制。

### 2.3 每份 DDL 的前置檢核 —— `dataval/precheck.py: run_precheck()`

在真正驗證前，先做**三層檢核**（存在性 → 可解析性 → 一致性），任何一層沒過，
這個 subject 就整個跳過、不產生報告：

1. **存在性**：DDL 能讀到；`samples/` 每張表都有對應 CSV。
2. **可解析性**：DDL 能被 `sqlglot` parse（`dataval/parser.py`）；CSV 表頭
   讀得出來；`relations.yaml` 是合法 YAML；`context.md` 有 front-matter
   與必填的「粒度」段落。
3. **一致性**：CSV 欄名是 DDL 欄位的子集；`relations.yaml` 裡的 `from`/`to`
   端點（本地部分）存在於 DDL；`cardinality` 值合法（`1:1`/`N:1`/`N:M`）。

三層都過，`run_precheck()` 會**順便把四件輸入轉成引擎可直接吃的結構**：
`relations_to_lineage()`（`precheck.py:142`）把 `relations.yaml` 轉成
declared lineage 格式；CSV 被轉型（`_coerce()`，空字串→`None`、`true/false`→
布林、純數字字串→`int`/`float`）放進 `result.samples`；`context.md` 的
front-matter 被拆成 `subject`/`domains`/`business_keys`。

無論通過與否，`run.py` 都會把檢核表寫成 `reports/<名>.precheck.md`（供人讀）；
沒通過時 console 會印出缺件明細，整個程式最後以 **exit code 2** 結束
（`run.py:528-532`），提醒「有輸入不齊全，未產生報告」。

> 這一步完全確定性、不碰 LLM——它是閘門區的最前哨，設計哲學是「連驗證資格
> 都不夠時，不要生出一份看似正式的報告」。

### 2.4 合併成 `InputCase` —— `run.py: load_input_v2()`

前置檢核通過的 subject，會把「四件輸入的結果」＋「可選的
`config/<域>/cases/<名>.yaml` 補充設定」合併成一個 `InputCase`。四件輸入是
**權威來源**：`business_keys` 以 `context.md` front-matter 為準、`lineage`
以 `relations.yaml` 轉出的為準（cases 的 legacy 設定只在沒宣告時補上）。
這裡也會呼叫 `merge_domain_erds()`（`run.py:316`）疊加 domain 的參考 ER 模型
（`config/<域>/erd/*.mmd`），只取「兩端表都出現在本次 DDL」的關係，供之後
的 lineage 建議候選比對。

### 2.5 驗證主流程 —— `dataval/engine.py: validate()`

這是整個工具的核心，一條線性管線，每個階段都往 `findings: list[Finding]`
裡加東西：

```text
parse_ddl(ddl)                          → Schema（表／欄位／型別／PK／sorting key）
load_glossary() / load_ssot()           → 依 domains 合併詞彙字典與 SSOT registry
                                           （Common 為基底，永遠載入）
SkillRegistry.load_compiled()           → 從 compiled_rules.json 載入本次
                                           domains 對應的規則
SkillRegistry.run(schema, llm, ...)     → 逐條規則執行：
                                             ```check   → 閘門，零 LLM
                                             ```check-llm → 顧問，呼叫 llm
                                             knowhow_py  → Python 函式跑複雜邏輯
business_keys 驗證                       → BUSINESS_KEY.METADATA
domain scope 檢查                        → DOMAIN.SCOPE
concept.run()                           → 顧問區：這個 schema 的「主體」抓對了嗎
production.run()                        → 命名對 production/ 既有基準（PRODUCTION.NAMING_CONSISTENCY）
prodgraph.run()                         → 併入本次 relations 後，正式區全域圖
                                           會不會出現循環／基數矛盾（PRODGRAPH.*）
flows.run()                             → 標註本次的表在哪些 domain E2E 流程的第幾站
lineage.run()                           → declared lineage 的確定性檢查
                                           （欄位存在、型別相容、循環）＋
                                           未宣告時的保守候選建議
subject_inference.run()                 → 啟發式偵測「看起來是權威表但 SSOT
                                           registry 沒登錄」的候選
_enforce_zone(f) 逐筆套用                → 見下段
findings.sort(...)                      → 穩定排序，同輸入永遠同順序
```

其中最關鍵的一段是 `_enforce_zone()`（`engine.py:75-96`）：

```python
def _enforce_zone(f: Finding) -> Finding:
    is_llm = (f.source == "llm")
    is_advisory = (f.zone == ZONE_ADVISORY)
    if is_llm or is_advisory:
        f.zone = ZONE_ADVISORY
        if f.status in ("fail", "warning"):
            f.status = "info"          # 顧問區永不擋，即使規則自己標成 fail
        f.severity = "info"
    else:
        f.zone = ZONE_GATING
    return f
```

這是「兩區分離」在程式層的第二道保險：**不管上游哪個模組不小心把 LLM
產出標成 `fail`／`blocking`，這裡都會強制降回 `info` 並轉進顧問區**。
第一道保險是設計上就讓 LLM 只出現在 `check-llm` 卡控與 `concept.py`，
執行到閘門區規則時 `llm` 參數根本用不到。兩道保險疊加，才有 README
說的「同一 DDL＋同一規則集，checking rule ID 結果必須一致」這個保證——
`tests/golden_test.py` 的 T2、T3 就是在守這件事。

### 2.6 輸出報告 —— `run.py: main()` 尾段 + `dataval/report.py`

`validate()` 回傳的 `findings` 會被寫成三種格式（`dataval/report.py` 的
`to_markdown` / `to_json` / `to_html`）：

- `<名>.report.md`：人讀，含摘要列（判定、通過/警告/失敗數）、
  checking rule ID 摘要、Lineage 表、依四類（結構/命名/最佳實踐/SSOT）分節
  的明細表。
- `<名>.report.json`：程式讀，`gating_zone.findings` / `advisory_zone.findings`
  分開存放——`merge_advisory.py` 靠比對這個檔案的 `gating_zone` 來確保合併
  顧問建議時閘門結果沒被動到。
- `<名>.report.html`：單檔互動（判定卡片、搜尋、fail/warning 篩選、
  分類摺疊），永遠會產生——即使沒接 LLM，顧問區會清楚標示「待補完」而不是
  空白或報錯。

沒接 LLM 時（`llm_on = type(llm).__name__ != "NullLLM"` 判 false），額外
產出 `<名>.advisory_prompt.md`（`dataval/advisory_export.py: build_advisory_prompt`），
把「有哪些 check-llm 規則被跳過」「有哪些 SSOT 未登錄候選」整理成一份
可以直接餵給 agent 的提示詞——這是步驟 5 的輸入。

同時每個 subject 會多產生一份 `<名>.subject_summary.md`
（`dataval/subject_summary.py: build_summary()`），概述這個 subject 的用途，
作為晉升正式區前的說明文件草稿。

跑完後 console 會逐一印出 `✅ 合規` / `❌ 不合規（會擋 N）`，不合規時附上
「卡下來的規則」清單。整個 `run.py` 的結束碼：`0` 全部合規、`1`（要加
`--strict`）存在不合規、`2` 有 subject 前置檢核沒過。

## 步驟 3：閱讀報告

打開 `reports/order.report.html`（或直接看 `.md`）。報告固定分兩區呈現：

- **閘門區（gating）**：`SKILL.structural_business_key`、
  `SKILL.naming_column_case`、`LINEAGE.CYCLE`、`PRODGRAPH.CYCLE` 這類——
  這些決定「✅ 合規」還是「❌ 不合規」。
- **顧問區（advisory）**：`FLOW.CONTEXT`（這張表在哪個 E2E 流程的第幾站）、
  `CONCEPT.SUBJECT`（主體抓對了沒）、`SKILL.naming_semantic` 這類——只是
  `ℹ️`/`💡` 提示，不影響判定。

用 `input/order` 的真實報告對照：報告開頭寫

```
判定：✅ 合規（會擋項目 0）
通過 33 · 警告 5 · 失敗 0 · 略過 5 · 提示 3
閘門區 39 項 · 顧問區 7 項
```

往下的「本次卡控摘要」只列出**有東西可講**的規則（全通過的規則不會出現在
這裡），例如 `SKILL.ssot_authority`（警告：`customer`/`product` 的權威表不在
本次 DDL——這是預期的，因為它們的權威在別的 domain）。

再看 `input/subscription`（刻意含違規的示範）的報告：

```
判定：❌ 不合規（會擋項目 11）
```

「擋下（不合規的原因）」逐條列出，例如：

- `SKILL.bp_money_decimal` 擋下 `billing_event`、`subscription`
  （金額欄位用了 `float`，違反「金額必須用 Decimal」）
- `SKILL.naming_columns_commented` 擋下三張表（欄位缺 `COMMENT`）
- `LINEAGE.TYPE_COMPATIBILITY` 擋下 lineage 欄位型別不相容

每一條會擋的 finding 在明細表裡都有**四問**：`expected`（規則要求什麼）、
`actual`（實際看到什麼）、`fix`（怎麼修）、`rationale`（為什麼設這條規則）——
對應 `dataval/model.py` 的 `Finding` dataclass 欄位，這是刻意設計成「不用
再回頭查規則檔就能動手修」。

## 步驟 4：不合規時，修正並重跑

直接照報告的 `fix` 欄修改 `input/<名>/` 裡的檔案（DDL、samples、
relations.yaml 或 context.md），改完重跑 `python run.py`。因為閘門區是
確定性的，同一份修正後的輸入永遠得到同一個結果，可以放心反覆迭代。
想查某條規則完整定義在講什麼，去 `config/<域>/knowhow/{gating,advisory}/<id>.md`
讀，或查 `docs/規則總覽.md` 的規則手冊。

---

## 步驟 5（可選）：沒接 LLM 時，補完顧問區

`run.py` 是獨立 subprocess，**刻意不繼承 agent 自己的 LLM**——這是為了保證
閘門區在 agent session 裡也是零 LLM。沒設 `DATAVAL_LLM_BASE_URL` 時：

1. `run.py` 已經產出 `reports/<名>.advisory_prompt.md`（步驟 2.6）。
2. Agent（讀這份 `CLAUDE.md` 的 Claude Code，或讀 `AGENTS.md` 的 opencode）
   用自己的 LLM 依提示詞內容產出 `reports/<名>.advisory_result.json`。
3. 執行：
   ```bash
   .venv/bin/python merge_advisory.py
   ```

`merge_advisory.py` 的關鍵是**閘門保護**（`merge_advisory.py:113-121`）：
合併前，它會用 `NullLLM()` 重跑一次 `validate()`，把重跑後的閘門
findings 跟合併前報告裡存的閘門 findings 逐項比對（`_canonical_gating()`
把每筆 finding 序列化成可排序比對的字串）。**只要有一條 checking rule ID
的結果不一樣，就整個拒絕寫入**，並印出合併前後的 rule ID 差異。這保證了
「顧問區的建議不管怎麼補，都不可能悄悄改變合規判定」。

通過保護後，會把 `advisory_result.json` 裡的 `naming_semantic` / `concept` /
`skills` 內容轉成 `Finding`（一律 `source="llm"`、`zone="advisory"`、
`status="info"`），取代原本「未接 LLM，略過語意卡控」的佔位訊息，重繪
三式報告。跑 `python merge_advisory.py --status`（若有支援）或看 console
輸出可確認「顧問區全數補完」。

## 步驟 6：晉升到正式區

```bash
.venv/bin/python run.py                     # 先確認最新報告合規
.venv/bin/python promote.py order           # 合規才能晉升
```

`promote.py` 做的事（對照原始碼 `promote.py`）：

1. **前提檢查**：`reports/<名>.report.json` 存在，且
   `summary.compliant == true`；不合規會被 `fail()` 直接擋掉
   （`promote.py:95-98`）。
2. **決定 domain**：從 `context.md` front-matter 的 `domains` 推斷（只宣告
   一個就自動用；宣告多個或沒宣告則要求 `--domain` 明確指定）。
3. **搬移三件**（不含 samples）到 `production/<DOMAIN>/<名>/`：
   `<名>.sql`、`<名>.relations.yaml`、`<名>.context.md`。樣本刻意**不**進
   正式區——樣本是驗證當下的證據，不是正式資產；改用 SHA256 存證。
4. **寫入 `_promotion.yaml`** 晉升記錄，裡面兩個關鍵欄位：
   - `gate_result_code`：閘門區所有 finding 的 `(rule|status|target)` 排序後
     整體雜湊（`promote.py: gate_result_code()`）——代表「這次晉升時，閘門
     檢查結果長什麼樣」。
   - `rule_version_code`：`build/compiled_rules.json` 內容雜湊
     （`dataval/prodgraph.py: current_rule_code()`）——代表「用的是哪一版
     規則」。

     這兩碼合起來是**因果保證**：之後規則演進了，只要比對
     `rule_version_code` 跟現行版本碼是否一致，就能機械判斷「這個 subject
     是不是用舊規則通過的、該不該建議重驗」——這正是步驟 7
     `production_audit.py` 在做的事。

晉升後，這個 subject 的表就成為**全域關聯圖**的一部分：之後任何新 subject
的 `relations.yaml` 若引用了它（跨 domain 三段式 `DOMAIN.table.col`），
`dataval/lineage.py` 會對 `production/<DOMAIN>/` 的已核准 DDL 做實檢
（表存在、欄位存在、型別相容）；`dataval/prodgraph.py` 也會在這個新 subject
加入後，檢查全域圖會不會出現循環（`PRODGRAPH.CYCLE`，會擋）或基數矛盾
（`PRODGRAPH.CARDINALITY_CONFLICT`，會擋），並提示「這張表改了會影響誰」
（`PRODGRAPH.IMPACT`，僅資訊）。

---

## 步驟 7：全區健檢（不常跑，但很重要）

```bash
.venv/bin/python production_audit.py
```

這不是在驗新 subject，是**掃整個已晉升的正式區**（`dataval/prodgraph.py: audit()`），
檢查：三件是否齊全、DDL 能否解析、有沒有斷鏈（`relations.yaml` 指向的上游
表在正式區找不到）、全域循環、基數矛盾，以及最重要的——**規則版本碼 drift**：
比對每個 subject `_promotion.yaml` 裡記的 `rule_version_code` 跟現行
`build/compiled_rules.json` 的雜湊，不一致就標記「建議重驗」（因為規則
演進後，舊的合規判定不再保證仍然合規）。輸出 `reports/production_audit.md`；
有 `fail` 等級的發現時 exit code 1。

---

## 步驟 8（可選）：新增或修改規則

只有在**治理需求本身變了**（例如要新增一條「金額欄位必須有幣別」的規則）
才需要這一步；日常驗證某份 DDL 不需要碰這裡。兩條路徑：

### 8a：人工直接寫

```bash
.venv/bin/python rules.py new <domain> <gating|advisory> <rule_id>
```

`rules.py: cmd_new()` 會從 `config/templates/skill_{gating,advisory}.template.md`
複製一份骨架到 `config/<domain>/knowhow/<zone>/<rule_id>.md`，填好
`id`/`category`/`enforcement` 佔位。人工編輯完後：

```bash
.venv/bin/python rules.py check    # = lint + compile
.venv/bin/python run.py
```

`lint_rules()`（`rules.py:90`）會檢查：檔頭三欄合法、id 唯一、四段人讀
規範齊全、恰好一個卡控區塊、gating 目錄只能放 blocking/warning、advisory
目錄只能放 advisory、`check` 動詞都在白名單內（見 `SKILL_AUTHORING.md` 第 3
節）、正則語法有效。任何一條沒過，`compiler.py` 會拒絕載入並印出原因。

### 8b：由 LLM 起草（drafts/ 流程）

```bash
.venv/bin/python rules.py draft <domain> <gating|advisory> <rule_id> "<需求描述>"
# 人工審閱 drafts/<rule_id>.md ……
.venv/bin/python rules.py adopt <rule_id>
```

`dataval/drafting.py: create_draft()` 把需求描述包成固定格式的 prompt；
接了 LLM 就直接產出 `drafts/<rule_id>.md`，沒接就產出
`drafts/<rule_id>.prompt.md` 交 agent 依格式生成草稿本體。草稿標記
`NEEDS_PY` 代表這條規則的邏輯超出宣告式 `check` 動詞能表達的範圍
（例如需要跨表遞迴偵測循環引用），要改寫成 `config/Common/knowhow_py/*.py`
的 Python 規則。`adopt_draft()`（`drafting.py:170`）用**跟 `rules.py check`
相同標準**的 `lint_one()` 把關，通過才搬進 `knowhow/`；全程留痕：
`drafts/LOG.md` 記「怎麼來的」，`rules_history/` 記「何時生效」，兩者以
`rule_id` 互相對照。**邊界不變：LLM 只出現在撰寫規則的當下，規則一旦進了
`knowhow/`，執行永遠是確定性的。**

## 常用指令速查

```bash
# 主線
.venv/bin/python run.py                          # 驗證 input/ 下所有 DDL
.venv/bin/python run.py --strict                 # 有不合規就 exit 1

# 顧問區補完（沒接 LLM 時）
.venv/bin/python merge_advisory.py

# 正式區
.venv/bin/python promote.py <名>                  # 晉升
.venv/bin/python promote.py <名> --update         # 重新晉升（保留前版記錄）
.venv/bin/python production_audit.py              # 全區健檢

# 規則維護
.venv/bin/python rules.py list                    # 盤點目前載入的所有規則
.venv/bin/python rules.py new <domain> <gating|advisory> <rule_id>
.venv/bin/python rules.py check                   # lint + compile
.venv/bin/python rules.py draft <domain> <gating|advisory> <rule_id> "<需求>"
.venv/bin/python rules.py adopt <rule_id>

# 測試
.venv/bin/python -m unittest discover -s tests -p "*_test.py"
```
